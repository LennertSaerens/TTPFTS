# Runtime feasibility report
This preregistration uses the fixed budgets in `experiments/final_config.json`, 100 repetitions, six algorithms, and the normalized 101-point grid (`--eval_points 100`). No HPC job was launched.
## Measurement methodology
The original anytime benchmark was contaminated by a one-off `paretoset` numba/JIT compile: the first fresh-process call paid about 2.6 s and the algorithm that happened to trigger it inherited that cost. The corrected measurements in `anytime_per_pull_costs.csv` were generated by `experiments/reports/measure_anytime_per_pull.py` as follows:
- Import/setup time is outside all timed regions.
- The numba-backed `paretoset` path is explicitly warmed on representative shapes before measuring any algorithm.
- Each bandit is then warmed past its own initial cheap phase before timing: TTPFTS runs `4*K + 100` untimed pulls, APE runs `K + 100` untimed pulls, and Uniform runs 100 untimed pulls. This measures production-relevant steady state rather than a short window dominated by mandatory round-robin warm-up.
- Reported values are medians of five repeats. Timed windows were 50,000 pulls for Uniform, 1,000 for APE, and 5,000 for each TTPFTS variant. Raw repeats are in `anytime_per_pull_measurements.csv`.

This also explains the apparent EgeExp3/TTPFTS inversion in short-window measurements: with only 1,000 timed pulls from a fresh TTPFTS bandit, EgeExp3 spends 800/1000 pulls in the cheap four-pulls-per-arm warm-up (K=200), whereas K=10 environments spend only 40/1000 there. APE has the same trap: its first K pulls are round-robin initialization with no pairwise b_t/c_t computation. On EgeExp3 the independently reproduced split was APE 2696.4 us/pull including warm-up versus 4470.4 us/pull steady-state; TTPFTS_KNOWN_VAR 24.3 versus 46.4; TTPFTS_UNKNOWN_VAR 40.9 versus 84.0. Since B=685,036, the 200-pull APE warm-up and 800-pull TTPFTS warm-up are only about 0.03% and 0.12% of the run respectively, so steady-state cost is the scientifically correct projection basis. After warming past posterior/initialization phases, EgeExp3 no longer drops below the smaller 2-D environments. Remaining tiny Uniform/TTPFTS inversions among equal or near-equal K are measurement noise at the sub-microsecond to few-microsecond scale; EgeExp4 is higher for TTPFTS because D=10.

## EGE measurements
EGE_SR and EGE_SH are fixed-budget algorithms re-run from scratch at every evaluated budget. I kept the prior local three-point timing (`B/100`, `B/10`, `B/4`) and linear fits in `ege_timing_measurements.csv`; those fits had R²≈0.997–1.0 and are still the appropriate EGE projection source. Projection details per environment/algorithm are in `runtime_projection.csv`.

## HPC sizing recommendation
The new `hpc/run_preregistered_final.slurm` keeps one array task per environment, `--partition=batch`, and `--exclude=master`, but now steers to the fast Zen 4 nodes with `--nodelist=node102,node103`. This intentionally avoids node001: the 2.5x slowdown assumption was only for the older Haswell node, while node102/node103 (EPYC 9634) should be much closer to local performance. I use a conservative **1.3x Zen 4 slowdown** for wall-time sizing.

The script now requests `--cpus-per-task=25`. Parallelism is over the 100 repetitions, so 25 workers gives exactly **4 repetitions per worker** for each environment/algorithm block. This is a cleaner load balance than 16 workers (uneven 6--7 repetitions/worker) and avoids the waste of 50 workers for the seven cheap environments. With 25 CPUs, all eight array tasks can fit across node102/node103 at once (8 * 25 = 200 CPUs across 336 logical CPUs), and SLURM can pack up to six tasks on one Zen 4 node without CPU oversubscription.

The longest projected task is still EgeExp3 at 96.53 core-hours. At 25 workers this is **3.86 local-equivalent wall-hours**; applying the 1.3x Zen 4 factor gives **5.02 hours**. The script requests `--time=12:00:00`, a >2x safety margin for scheduler placement, Python/joblib overhead, NFS variance, and measurement error without being tight enough to risk losing a long EgeExp3 run. If the Zen 4 nodes are unavailable, the job waits rather than silently running on node001.

The script now requests `--mem=24G`. Output size is small (484,800 total rows across the whole design); memory is dominated by joblib worker processes and per-worker bandit state. The largest state is EgeExp3 APE/TTPFTS with K=200, D=2, including transient 200x200 APE matrices, which is small relative to Python process overhead. 24G leaves roughly 1G per worker plus headroom, while six packed tasks would reserve only 144G on a 755G Zen 4 node, so memory will not be the packing bottleneck. BLAS thread counts remain pinned to 1 while `--n_jobs` uses the allocated CPUs for repetition-level parallelism.
## Feasibility concerns
- APE on EgeExp3 is still the dominant cost because K=200 and B=685036; after removing short-window warm-up dilution it projects to the largest single cell.
- The final config, budgets, and algorithms are unchanged; only runtime/resource artifacts were regenerated.
- The script writes to a hash-suffixed `results_preregistered_final_<config>` directory and logs commit/config hashes for provenance.
